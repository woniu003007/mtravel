# 销售收客订单表说明

本文件说明 `013_sales_booking_order_schema.sql` 中的销售收客订单主链路表。收客订单是团队下客户报名、游客名单、应收金额和后续计调履约、财务应收的来源。

## 设计原则

- 收客订单必须挂在正式团队 `sales_teams` 下，一个团队可以有多个订单。
- 页面按订单信息、行程说明、导游相关、客户信息、价格信息、酒店信息、附加说明、费用变更记录、游客名单分区保存。
- 订单主表只保存订单抬头、人数和汇总金额；订单原始价格和后续应收调整统一写入 `sales_order_charge_lines`。
- `sales_order_price_lines`、`sales_order_fee_changes` 为早期拆表结构，当前保留兼容和历史迁移，不再作为新代码读写来源。
- 保存订单后刷新团队实收人数和剩余人数；取消订单不占用团队余位。
- 拼团后，来源团队原订单保留在来源团且继续参与来源团人数、收入和毛利统计；目标团队下生成 `merge_child` 拼团子订单，并按拼团确认页价格参与目标团人数、收入和毛利统计。
- 一个来源订单可以拼到多个目标团队；多个来源订单也可以一次批量拼到多个目标团队，实际生成“来源订单 x 目标团队”的子订单关系。重复来源订单和目标团队组合跳过，其它组合继续执行。
- 转团是订单归属迁移，订单收入、游客名单和应收明细随订单迁到目标团队，不生成拼团子订单。
- 订单状态、应收明细归类、游客类型和费用变更状态均通过 `CHECK` 约束限制。
- 所有业务表带 `tenant_id`，查询和修改必须带租户边界。
- 业务数据默认软删除，普通删除不物理移除记录。

## 表清单

| 表名 | 作用 |
| --- | --- |
| `sales_orders` | 销售收客订单主表，保存客户、接送、行程、导游、酒店、人数、应收、已收、余额和订单状态。 |
| `sales_order_charge_lines` | 订单应收明细表，统一保存原始订单价格和后续加收、退减等应收调整。 |
| `sales_order_guests` | 订单游客名单表，保存游客证件、客户类型、分房、领队和身份证校验结果。 |
| `sales_order_price_lines` | 早期订单价格明细兼容表，保留用于历史迁移和旧数据核对。 |
| `sales_order_fee_changes` | 早期费用变更兼容表，保留用于历史迁移和旧数据核对。 |
| `sales_order_transfer_logs` | 订单团队流转日志表，保存拼团、转团产生的来源订单、原团队、目标团队和目标订单关系。 |

## 拼团和转团业务口径

### 拼团

拼团用于把来源订单挂到一个或多个目标执行团队，生成目标团拼团子订单并保留来源订单关系。它不是单纯改团队 ID，也不是修正录错团队。

拼团后的关系：

```text
来源团队原订单
  -> 拼团关系日志
  -> 目标团队拼团子订单
```

统计口径：

- 来源团队原订单保留客户来源、业务员、收客计调、原始报名信息和拼团追溯信息。
- 新拼团不再把来源团队原订单写入 `order_role = merge_source`。历史 `merge_source` 只作为旧数据留痕角色，继续参与来源团队收入、人数、游客名单和团队毛利统计。
- 目标团队拼团子订单写入 `order_role = merge_child`，参与目标团队收入、人数、游客名单、团队执行和团队毛利统计。
- 一个来源订单可以同时拼到多个目标团队，多个来源订单也可以同时拼到多个目标团队，后端按“目标团队 x 来源订单”矩阵生成子订单。
- 目标团队拼团子订单复制来源订单游客名单，但不复制来源订单原 `base_price` 应收明细；只按拼团确认页的价格类型和拼团单价生成一条目标子订单 `base_price` 明细。
- 拼团单价为 `0` 时，目标子订单应收为 `0`，只计人数；拼团单价手填时，目标子订单应收 = 单价 x 来源订单人数。
- 拼团子订单 `received_amount` 默认为 `0`，不能复制来源订单已收金额；真实收款后续由收款记录和核销分摊回写。
- 拼团关系必须通过 `sales_order_transfer_logs` 追溯，`sales_orders.original_order_info` 只作为页面摘要展示。

### 转团

转团用于把订单从原团队整体迁移到另一个团队。常见场景包括客户改团期、录单选错团队、原团队取消或停售后换团。

转团后的关系：

```text
原团队订单
  -> 迁移为目标团队订单
  -> 流转日志记录原团队和目标团队
```

统计口径：

- 转团不生成拼团子订单。
- 订单、应收明细和游客名单的 `team_id` 跟随订单迁到目标团队。
- 原团队只保留转出日志，不再统计该订单人数、收入、游客名单和毛利。

### 团队毛利

拼团团队的收入和成本按老系统实测口径分别落在各自团队。

```text
团队总收入 = 本团队有效订单收入 + 拼入本团队的有效子订单收入
团队总成本 = 本团队实际发生的用车、导游、酒店、门票、餐等成本
团队毛利 = 团队总收入 - 团队总成本
团队毛利率 = 团队毛利 / 团队总收入 * 100%
```

来源订单收入继续留在来源团；目标团子订单按拼团价计收入。若目标团子订单拼团价为 `0` 且成本录在目标团，目标团毛利允许为负，这是老系统当前口径的真实表现。若拼团确认页手填价格，来源团收入和目标团子订单收入会同时存在，跨团汇总时需按业务规则选择统计口径。

## 联动规则

- 新增或修改订单后，按未取消订单汇总团队 `used_seats`；订单保存时优先按原始价格行 `occupy_seat = true` 的数量计算订单占位人数，没有占位价格行时再退回游客名单人数。
- 团队人数、订单列表和后续收入统计默认统计 `order_role IN ('normal', 'merge_child', 'merge_source')`；`merge_source` 仅用于历史来源留痕，不再作为统计过滤角色。
- `remaining_seats = total_seats - used_seats`，允许出现负数用于暴露超收问题。
- 新增订单应收按 `sales_order_charge_lines.line_kind = 'base_price'` 的 `amount` 合计。
- 修改订单时重建 `base_price` 行，但保留 `adjustment` 历史流水；订单应收按原始价格合计加 `approved` 调整金额计算。
- 生效费用变更按 `line_kind = 'adjustment'` 且 `status = 'approved'` 汇总到订单应收；作废、驳回和待处理记录不计入应收。
- 费用变更统计按费用项目、变更方向、客户、团队、登记时间和登记人汇总，不使用变更方向承担原因分类。
- 真实收款不写入 `sales_order_charge_lines`，后续财务收款应单独设计收款记录和核销分配表，再回写订单已收和余额。
- 订单余额按应收减已收计算。
- AI 辅助录入只回填草稿，不自动保存订单、价格或游客名单。
- 拼团操作保留来源订单，并按目标团队和来源订单矩阵在目标团队下生成子订单；转团操作迁移订单当前归属，并同步订单收入明细和游客名单的团队 ID。
- 拼团、转团必须写入 `sales_order_transfer_logs`，不能只依赖 `sales_orders.original_order_info` 或订单备注追溯。
- 后续团队账单和统计查询必须明确区分来源团收入、目标团拼团子订单收入和跨团汇总口径，不能再用 `merge_source` 过滤来源订单。
- 订单管理页标记只更新 `sales_orders.tagging`，用于销售人员筛选重点订单，不改变订单状态、团队归属、应收金额或收款状态。
- 收款、电子合同、打印和费用变更审批后续在本表基础上继续扩展。
