# 接口统一返回格式与状态码规范

本文档定义后端接口的统一响应格式、状态码含义和后续代码实现方向。所有业务接口都应按本规范返回，避免前端针对不同接口写不同解析逻辑。

## 统一响应格式

所有 JSON 接口统一返回以下结构：

```json
{
  "code": 0,
  "data": {},
  "error": null,
  "message": "ok"
}
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | number | 业务状态码。成功固定为 `0`，失败使用本规范定义的错误码。 |
| `data` | any | 接口业务数据。无返回数据时为 `null`。 |
| `error` | string/object/null | 错误详情。成功时为 `null`；失败时放错误原因或字段错误详情。 |
| `message` | string | 前端可展示提示。成功默认 `ok`；失败时放明确、可读的错误提示。 |

## HTTP 状态与业务状态码

接口成功时：

- HTTP 状态码：`200`
- 响应体 `code`：`0`

接口失败时：

- HTTP 状态码应与响应体 `code` 保持一致。
- 前端优先读取响应体 `message` 或 `error` 展示错误原因。

## 状态码定义

| code | HTTP 状态 | 名称 | 使用场景 |
| --- | --- | --- | --- |
| `0` | `200` | 成功 | 请求处理成功。 |
| `400` | `400` | 参数错误 | 请求参数缺失、格式错误、字段校验失败、业务参数不合法。 |
| `401` | `401` | 未登录 | 未登录、登录过期、Token 无效、Token 被注销。 |
| `403` | `403` | 无权限 | 已登录，但没有访问当前接口或数据的权限。 |
| `404` | `404` | 资源不存在 | 查询、修改、删除的数据不存在，或已被软删除。 |
| `409` | `409` | 数据冲突 | 唯一字段重复、状态冲突、并发修改冲突等。 |
| `500` | `500` | 服务器内部错误 | 未预期异常、服务端程序错误、第三方服务不可用且未被业务兜底。 |

## 响应示例

成功返回列表：

```json
{
  "code": 0,
  "data": {
    "items": [],
    "total": 0
  },
  "error": null,
  "message": "ok"
}
```

参数错误：

```json
{
  "code": 400,
  "data": null,
  "error": "客户分类名称不能为空",
  "message": "客户分类名称不能为空"
}
```

登录失效：

```json
{
  "code": 401,
  "data": null,
  "error": "登录状态已失效",
  "message": "登录状态已失效"
}
```

资源不存在：

```json
{
  "code": 404,
  "data": null,
  "error": "客户分类不存在或已删除",
  "message": "客户分类不存在或已删除"
}
```

数据冲突：

```json
{
  "code": 409,
  "data": null,
  "error": "客户分类名称已存在",
  "message": "客户分类名称已存在"
}
```

服务器内部错误：

```json
{
  "code": 500,
  "data": null,
  "error": "服务器内部错误",
  "message": "服务器内部错误"
}
```

## 后端实现约定

后续代码改造按以下方向执行：

- `ApiResponse.ok(data)` 固定返回 `code = 0`、`message = "ok"`。
- `ApiResponse.fail(...)` 不再统一返回 `-1`，必须接收明确状态码。
- 新增 `ResultCode` 枚举，集中维护 `code`、HTTP 状态和默认提示。
- `BizException` 支持携带 `ResultCode`，业务层抛异常时能表达 `400`、`404`、`409` 等不同错误。
- `GlobalExceptionHandler` 按异常类型返回统一响应体，避免每个控制器单独处理错误格式。
- `JwtAuthenticationFilter` 不再手写 JSON 字符串，登录失效也使用统一响应体。

## 前端对接约定

前端请求层按以下规则解析：

- `code = 0` 表示业务成功。
- `code != 0` 表示业务失败。
- 失败时优先展示 `message`；如果 `message` 为空，再展示 `error`。
- 分页、列表、详情、删除等接口都必须使用同一响应结构。

当前前端请求配置已按 `successCode = 0` 识别成功，因此后端成功码继续固定为 `0`。

## 接口方法约定

本项目后台接口统一采用 `GET + POST`，暂不使用 `PUT`、`PATCH`、`DELETE`。

| 请求方法 | 用途 | 示例 |
| --- | --- | --- |
| `GET` | 查询、详情、下拉、统计预览等不改数据的接口。 | `GET /customer/category/page` |
| `POST` | 新增、修改、删除、启用、停用、审核、撤回、导入、导出任务提交等会产生业务动作的接口。 | `POST /customer/category/update?id=1` |

操作日志不能只按 HTTP 方法判断业务动作，因为多个写操作都使用 `POST`。后端需要通过路径或注解记录真实操作类型，例如 `新增`、`修改`、`删除`、`审核`、`导入`。
