# 老系统调研：拼团订单与团队业务逻辑

调研日期：2026-06-15

## 1. 团队类型理解

老系统里的 `散拼`、`散团`、`整团`、`单项` 更像是团队/业务类型标签，不是完全不同的数据体系。

目前观察到：

- `整团`：一个客户或一个主体形成的独立团队。
- `散拼`：多个客户订单可以拼到同一个出行团队里。
- `散团`：也是团队类型之一，录入方式与其他团队后续流程基本共用。
- `单项`：新增页面的基本信息较简单，但保存后仍然进入团队/订单后续流程。

结论：新系统建表时，团队主表和订单主表可以共用一套结构，通过团队类型、订单类型、拼团状态区分业务场景。

## 2. 散拼团队预订

`销售管理 / 散拼团队预订` 不是只展示散拼团。

实际列表里能看到：

- 散拼
- 散团
- 整团
- 单项

它更像一个“团队预订/收客工作台”，用于从团队角度查看可预订、已收客、团队进度等信息。

结论：老系统这个菜单名有误导性。新系统如果保留，可以考虑改成 `团队预订工作台` 或 `团队收客预订`。

## 3. 拼团订单管理

`销售管理 / 拼团订单` 页面主要用于管理准备拼到其他团队里的订单。

页面有几个标签：

- `全部`
- `未拼团`
- `已拼团`
- `子订单`
- `按团展示`

目前调研结论：

- `拼团订单` 按钮不是“执行拼团”，而是“新增一条准备拼团的订单”。
- 点击 `拼团订单` 后，老系统进入 `单项业务` 新增页。
- 保存后，订单会进入 `拼团订单管理` 列表。
- 如果还没有选择目标团队，则可以理解为待拼团订单。

重要说明：老系统通过 `拼团订单` 新建时显示为 `单项`，但业务上不应简单理解成“拼团订单只能是单项团”。这是老系统复用了单项业务录入页导致的表现。

## 4. 未拼团订单如何产生

实操验证流程：

1. 进入 `销售管理 / 拼团订单`。
2. 点击右上角 `拼团订单`。
3. 系统打开 `单项业务` 新增页。
4. 填写订单信息并保存。
5. 保存后订单进入 `拼团订单管理`。
6. 未执行拼团操作前，订单属于待拼团状态。

本次测试产生过的测试单：

- `测试未拼团订单-0615-只演示不拼团`
- `可见演示未拼团订单-0615`

结论：进入这个列表的关键不是“单项”两个字，而是订单来源于拼团订单入口，并且还没有完成目标团队绑定。

## 5. 拼团操作

`拼团操作` 的作用是：把已创建的拼团订单，挂到某个目标团队下面。

实操验证流程：

1. 在 `未拼团` 列表勾选一条订单。
2. 点击右上角 `拼团操作`。
3. 系统弹出窗口，标题为：`将选择的订单拼到其它团队`。
4. 在 `选择团期` 页签里勾选目标团队。
5. 切换到 `拼团操作` 页签。
6. 点击 `执行拼团`。
7. 系统提示：`分团完成!`
8. 原订单的 `拼团信息` 列出现目标团队链接。

结论：`拼团操作` 不是新增订单，也不是新增团队，而是建立“原订单 -> 目标团队”的拼团关系。

## 6. 未拼团标签页不完全可靠

实操后发现：执行拼团后，订单可能仍然显示在 `未拼团` 标签页里，但 `拼团信息` 已经出现目标团队链接。

所以判断订单是否已经拼团，不能只看标签页，应该看：

- `拼团信息` 是否为空
- 是否已经有关联目标团队
- 是否生成了目标团下的订单记录

结论：新系统不要照搬老系统这个过滤逻辑。应明确字段：

- `待拼团`
- `已拼团`
- `子订单`

并用状态字段严格控制列表归属。

## 7. 子订单概念

`子订单` 可以理解为：原订单拼到目标团队后，在目标团队下面生成或挂接出来的订单记录。

业务关系是：

`原始订单` -> `拼团操作` -> `目标团队` -> `目标团队下的子订单`

其中：

- 原始订单保留客户来源、原始金额、备注等信息。
- 目标团队负责实际出行、计调履约、团队成本和排团。
- 子订单用于在目标团队下体现这个客户订单。

结论：新系统不建议简单复制一条订单后断开关系，应明确保存来源关系。

业务口径补充：

- `子订单` 不是人数更少、金额更小的订单，而是由原订单通过拼团动作派生出来的目标团承接订单。
- 页面上如果直接显示 `子订单`，业务人员容易误解；建议展示为 `拼团子订单` 或 `目标团订单`。
- 例如订单原本在团 A，拼到团 B 后，团 A 的原订单保留为来源记录，团 B 下生成一条拼团子订单。
- 如果业务目标是把订单从团 A 完整迁到团 B，不保留目标团子订单关系，那属于 `转团`，不是 `拼团`。

建议字段：

- `source_order_id`：原始订单
- `target_group_id`：目标团队
- `child_order_id`：目标团队下生成的订单
- `combine_status`：待拼团、已拼团、子订单
- `combine_time`：拼团时间
- `combine_operator_id`：操作人

### 7.1 拼团目标团队的新系统优化口径

后续实操确认到：老系统允许一个来源订单在拼团操作中勾选多个目标团队，并生成多个目标团队下的拼团订单。这个能力本身可以保留，但老系统页面没有清晰要求把游客和金额拆到不同目标团队，存在完整游客和完整金额被复制到多个目标团队的风险。

新系统不照搬老系统“一个来源订单可勾选多个目标团队”的歧义交互。当前按更清晰的完整订单拼团实现：

- 一个来源订单一次只能拼到一个目标团队。
- 多个来源订单可以批量拼到同一个目标团队。
- 如果后续确实要把一个订单分到多个目标团队，必须先做正式拆单功能，把游客、人数、金额和收款关系拆清楚，再分别拼团。
- 来源订单保留为 `merge_source` 追溯记录，不参与来源团队收入、人数、名单和毛利统计。
- 目标团队子订单为 `merge_child`，承接完整来源订单的游客和应收金额，参与目标团队收入、人数、名单和毛利统计。
- 目标子订单不复制来源订单已收金额，真实收款仍由后续收款记录和核销分摊处理。

## 8. 拼团、转团、复制团队的区别

目前理解如下：

- `拼团操作`：把一个待拼团订单挂到目标团队下面，形成拼团关系或子订单。
- `转团操作`：更像是把订单从当前团队转移到另一个团队，重点是订单归属变化。
- `复制团队`：复制团队基础信息生成一个新团队，原团队不变。

其中 `拼团操作` 已实操验证；`转团操作` 和 `复制团队` 还需要后续继续实操确认细节。

### 8.1 拼团的业务意义

拼团的核心不是“改错团队”，而是把多个来源不同、客户不同、报名时间不同的订单，合并到一个实际出行团队里执行。

典型场景：

- 客户 A 报名 3 人。
- 客户 B 报名 5 人。
- 客户 C 报名 2 人。
- 这些客人最终使用同一辆车、同一个导游、同一套行程、同一个出团日期出行。

此时目标团队承担实际执行：用车、导游、酒店、门票、餐、团队安排和成本都发生在目标团队。来源订单仍要保留客户来源、业务员、收客计调、原始应收和报名痕迹。

因此新系统口径为：

- 原订单：保留来源和销售记录。
- 拼团子订单：挂在目标团队下，参与目标团队执行、人数、名单、团队应收和毛利统计。
- 拼团关系日志：保存原订单、原团队、目标团队、子订单、操作人和操作时间。

### 8.2 转团的业务意义

转团的核心是订单归属变更，适用于“订单本来属于团 A，现在应该属于团 B”的场景。

典型场景：

- 客户改出发日期，需要换到另一个团期。
- 录单时选错团队，需要纠正。
- 原团队取消、停售或人数不足，需要把订单迁到另一个可发团队。

转团后，订单本身迁到新团队，不生成拼团子订单。原团队只通过流转日志保留转出痕迹，不再参与该订单人数、游客名单、收入和团队毛利统计。

### 8.3 收入、人数和毛利统计口径

拼团后，收入和成本必须落在同一个实际执行团队上，否则团队毛利会失真。

正确口径：

- 团 A 原订单：只做来源追溯，不参与团 A 收入、人数、名单和毛利统计。
- 团 B 拼团子订单：参与团 B 收入、人数、名单、团队执行和毛利统计。
- 团 B 成本：用车、导游、酒店、门票、餐等实际执行成本归团 B。

团队毛利计算：

```text
团队总收入 = 本团队有效订单收入 + 拼入本团队的有效子订单收入
团队总成本 = 本团队实际发生的用车、导游、酒店、门票、餐等成本
团队毛利 = 团队总收入 - 团队总成本
团队毛利率 = 团队毛利 / 团队总收入 * 100%
```

禁止口径：

- 原订单在团 A 算一次收入，子订单在团 B 又算一次收入，导致收入重复。
- 收入仍留在团 A，成本发生在团 B，导致团 A 毛利虚高、团 B 毛利虚低。

## 9. 新系统设计建议

新系统不要完全照搬老系统菜单名和状态判断，应按真实业务关系设计：

- 团队主表统一管理 `整团 / 散拼 / 散团 / 单项`。
- 订单主表统一管理客户订单。
- 拼团关系单独记录，不要只靠订单备注或页面显示判断。
- 待拼团订单池明确展示“还没选目标团队”的订单。
- 已拼团列表明确展示“原订单拼到了哪个目标团队”。
- 子订单列表明确展示“目标团队下有哪些来源订单”。
- 团队收入、人数、游客名单和毛利统计必须过滤来源保留订单，只统计当前团队有效承接订单和拼团子订单，避免重复计算。

推荐页面命名：

- `待拼团订单`
- `选择目标团队`
- `执行拼团`
- `已拼团订单`
- `拼团子订单`
- `按目标团队查看`

## 10. 待继续确认

后续需要继续问甲方或实操确认：

- 是否需要在后续版本支持正式拆单后再把一个订单分到多个目标团队。
- 是否允许来源订单只拆出部分游客并保留未分配游客；当前不支持，必须通过未来拆单功能单独设计。
- 执行拼团后，原订单是否还能修改人数、金额、游客名单。
- 子订单金额是否继承原订单，还是可以单独变更。
- 子订单取消后，原订单如何回退。
- 转团操作是否会保留原团队记录，还是直接迁移订单归属。
- 甲方是否接受把老系统 `拼团订单` 改名为更直白的 `待拼团订单`。
