# 老系统调研：团队主链路跨模块建表依据

调研日期：2026-06-22

本文只用于后续建表前确认，不是 DDL，也不直接代表最终表结构。

## 1. 为什么要扩大调研范围

团队、团期和订单不是孤立模块。老系统里同一个团队会被销售、计调、财务、统计反复使用：

- 销售看团队、订单、散拼预订、拼团订单、费用变更、历史团队、团号日志、游客名单。
- 计调看团队安排、团队审核，以及导游、大交通、住宿、用车、景区、用餐、其他、自费、购物、地接这些执行项。
- 财务看团队审核、团队预付款、应收、应付、收款、付款、发票、导游备用金、导游结算、购物返佣、收支进度。
- 统计看团队进度、收客、利润、资源采购、账款、导游、收付款汇总、报表中心。

结论：不能只按“团期页面”建一张窄表。需要先设计一条统一主链路：

`产品模板 -> 团队 -> 订单 -> 游客 -> 团队安排 -> 成本/应收应付 -> 收付款/发票/结算 -> 统计`

## 2. 老系统团队类型结论

老系统 `销售管理 / 团队管理` 使用同一个团队列表，不同类型通过 `LineType` 区分：

- `2`：散拼
- `3`：整团
- `4`：散团
- `5`：单项

散拼、整团、散团共用新增页面。单项新增页面字段不同，但保存后仍进入同一个团队列表。

结论：

- 新系统不应为散拼、整团、散团、单项拆四套主表。
- 应使用统一团队主表，通过 `team_type` 区分。
- 单项业务特殊字段可以放到订单表或单项补充表，不污染团队主表。
- 产品下的团期管理本质是批量生成可收客团队，按老系统观察默认生成散拼团队。

## 3. 销售菜单对表设计的要求

### 团队管理

列表字段包括类型、团号、客户、团队名称、天数、开始、结束、出发地、预控/实收、导游信息、各类安排状态和进度。

团队主表至少要保存或能快速关联：

- 团队类型、团号、团队名称。
- 产品、业务类型、国内/国际、接待标准、产品主题。
- 出团日期、结束日期、旅游天数。
- 出发地或接团城市。
- 预控人数、实收人数、剩余人数。
- 部门、业务员、操作计调、导游摘要。
- 团队状态：未发团、已发团、停售、取消。
- 流程进度：团队安排、导游报账、计调审核、财务审核。

### 团期管理

团期页面挂在产品下，字段包括团号、发团日期、操作计调、状态、总位/余位、单房差、客户类型、成人、儿童、儿童不占床、老人、附加费用。

设计要求：

- 团期创建后应生成团队记录，而不是生成一张孤立团期表。
- 团期价格应按 `团队 + 客户分类` 维护。
- 总位、余位和价格要支持单字段修改，不能每次保存重建整个产品或全部团期。

### 订单管理和拼团订单

订单列表字段包括发团日期、订单信息、酒店信息、接送备注、客源地、客人、人数、价格详情、应收、已收、余额、费用说明、订单备注、下单人、状态。

设计要求：

- 订单必须挂团队 ID。
- 一个团队可以有多个订单。
- 一个订单可以有多个游客。
- 订单需要独立状态：未处理、已确认、已取消。
- 拼团订单需要记录原始订单、目标团队、拼团关系或转团关系，不能只改团队 ID 后丢失轨迹。
- 费用变更要独立记录，影响订单应收和客户授信占用。

### 游客和名单查重

游客信息包括姓名、英文名、身份证号、护照号、性别、成人/儿童、出生年月、年龄、联系电话、地址、客人标签。

设计要求：

- 游客基础信息应独立表保存。
- 订单游客关系要保存游客在本订单中的身份类型和备注。
- 名单查重要能按姓名、证件号、手机号、团队、订单查询。

## 4. 计调菜单对表设计的要求

团队安排列表和团队审核都围绕团队展开，并按以下执行项进入明细：

- 导游
- 大交通
- 住宿
- 用车
- 景区
- 用餐
- 其他
- 自费
- 购物
- 地接

设计要求：

- 正式团队安排不能复用产品模板安排表，必须有团队实际安排表。
- 团队安排明细需要统一表承接资源类型、供应商、资源、日期、数量、价格、备注、责任人。
- 价格明细要支持多行，因为酒店、用车、购物、自费等都可能一项下面多条费用。
- 成本归属要支持全团、单订单、多订单分摊，后续才能处理一个团队多个客户订单分别承担成本的问题。
- 安排状态要能支持列表中的图标状态和团队进度统计。

## 5. 财务菜单对表设计的要求

### 团队审核

财务团队审核页面展示团队应收、预算成本、实际成本、自费加点、购物消费、导服费、团队毛利、公司利润等。

设计要求：

- 团队应收来自订单和订单费用变更。
- 预算成本来自排团或安排阶段的预算。
- 实际成本来自导游报账、计调确认、财务确认后的实际成本。
- 自费和购物要单独保留收入、成本、导游提成、公司返佣、公司利润口径。

### 应收账款

应收按客户单位汇总，也能查看明细到团队/订单。

设计要求：

- 应收明细应以订单为主，挂团队、客户、业务员、下单人、部门。
- 收款记录要能冲减应收余额。
- 费用变更要能刷新应收和客户授信占用。

### 应付账款和成本明细

应付按供应商汇总，也能明细到团队/订单/费用项。

设计要求：

- 应付来源主要是团队安排实际成本。
- 每条成本要区分现付、挂账、已付、余款。
- 成本要挂资源类型、供应商、团队、订单归属、计调、导游。
- 付款记录要能冲减应付余额。

### 导游备用金和导游结算

导游备用金看团队、导游、计调、合计现付、备用金、应付、已付、余额。

导游结算看备用金、导游现付、导游收入、导游上交、现收现退、财务费用、代收团款、交通、门票、房费、车费、餐费、其它、地接、导服、加点、购物、奖罚等。

设计要求：

- 导游备用金应独立申请/支付/核销表。
- 导游手机报账上传的票据和费用明细，需要进入导游报账表，再由计调和财务审核。
- 导游结算不能只放一个总金额，要能追溯到费用项目。

### 收款、付款、发票、银行现金账

设计要求：

- 收款记录支持公司收款、导游现结、导游代收。
- 付款记录支持公司付款、导游现付、预付款、企业码。
- 收付款要挂银行账号、项目、往来单位、团队、订单或成本明细。
- 发票需要区分客户开票和供应商付款发票。
- 银行现金账可以由收付款记录生成或引用，不能脱离业务单据孤立记账。

## 6. 统计菜单对表设计的要求

统计页面主要按日期、部门、业务类型、计调、导游、团队类型、财务审核状态统计。

设计要求：

- 源表必须稳定保存统计维度：部门、业务类型、团队类型、出团日期、财务审核日期、操作计调、导游、客户、供应商、资源类型。
- 大数据量下不要统计页每次实时扫全量明细。
- 第一版可以先基于索引查询实时聚合。
- 数据量变大后，应增加日快照或统计汇总表，例如团队进度日汇总、收客日汇总、利润日汇总、资源采购日汇总、收付款日汇总。

## 7. 建议的核心表分层

第一层：销售源头

- `sales_teams`：统一团队主表，保存散拼、整团、散团、单项。
- `sales_team_prices`：团队按客户分类的价格。
- `sales_team_status_logs`：团队状态和进度日志。
- `sales_team_no_logs`：团号生成和变更日志。

第二层：订单和游客

- `sales_orders`：订单主表。
- `sales_order_price_lines`：订单价格明细。
- `sales_order_fee_changes`：订单费用变更。
- `sales_order_guests`：订单游客名单。
- `sales_order_transfer_logs`：拼团、转团、复制团队等订单/团队关系变更日志。

第三层：计调实际安排

- `dispatch_team_arrangements`：团队安排主明细，按导游、大交通、住宿、用车、景区、用餐、其他、自费、购物、地接统一承接。
- `dispatch_team_arrangement_price_lines`：安排费用明细。
- `dispatch_team_arrangement_order_allocations`：安排成本分摊到订单的明细。
- `dispatch_team_guides`：团队导游、领队、全陪等人员关系。

第四层：财务结算

- `finance_receivable_items`：应收明细，主要来自订单和费用变更。
- `finance_payable_items`：应付明细，主要来自团队安排实际成本。
- `finance_income_records`：收款记录。
- `finance_payment_records`：付款记录。
- `finance_invoice_records`：客户开票记录。
- `finance_supplier_invoice_records`：供应商发票记录。
- `finance_guide_imprests`：导游备用金。
- `finance_guide_settlement_items`：导游结算明细。
- `finance_shopping_rebates`：购物返佣明细。

第五层：统计汇总

- 先通过源表索引支撑查询。
- 数据量上来后再增加按天、部门、业务类型、团队类型、计调、导游、客户、供应商聚合的统计快照表。

## 8. 表设计必须保留的公共字段和索引方向

核心业务表必须有：

- `tenant_id`
- `id`
- `is_deleted`
- `created_at`
- `created_by`
- `updated_at`
- `updated_by`

团队相关常用索引方向：

- `tenant_id, is_deleted, departure_date`
- `tenant_id, is_deleted, team_type, departure_date`
- `tenant_id, is_deleted, group_no`
- `tenant_id, is_deleted, operator_id, departure_date`
- `tenant_id, is_deleted, department_id, business_type_id, departure_date`

订单相关常用索引方向：

- `tenant_id, is_deleted, team_id`
- `tenant_id, is_deleted, customer_id, status`
- `tenant_id, is_deleted, order_no`
- `tenant_id, is_deleted, sales_employee_id, created_at`

财务相关常用索引方向：

- `tenant_id, is_deleted, team_id`
- `tenant_id, is_deleted, order_id`
- `tenant_id, is_deleted, supplier_id`
- `tenant_id, is_deleted, customer_id`
- `tenant_id, is_deleted, business_date`
- `tenant_id, is_deleted, audit_status`

## 9. 下一步建议

不要马上建一堆财务和统计表。建议按顺序推进：

1. 先确认统一主链路表设计：团队、团队价格、订单、游客、订单费用变更、团队状态日志。
2. 再设计正式团队安排表，承接导游、交通、住宿、用车、景区、用餐、其他、自费、购物、地接。
3. 再设计应收、应付、收付款、发票、导游备用金、导游结算。
4. 最后设计统计汇总表或快照表。

当前如果要开始开发 `团期管理`，第一批不应新增独立 `sales_team_schedules`，而应围绕 `sales_teams` 和 `sales_team_prices` 建表。团期只是产品下批量生成团队的操作入口。

## 10. 待确认问题

- 散团和整团在甲方业务上是否只是团队类型标签，还是报价、收客、统计口径有差异。
- 单项业务是否继续保留“一页录团队、订单、游客、价格”的录入体验。
- 拼团和转团是否必须保留原始订单轨迹，建议保留。
- 团队进度是否允许人工改状态，还是由安排、报账、审核动作自动推进。
- 成本分摊是否需要首版支持多订单分摊，建议在表结构上预留。
- 财务统计首版是否接受实时聚合，还是一开始就做日汇总快照。
