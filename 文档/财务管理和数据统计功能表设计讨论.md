# 财务管理和数据统计功能表设计讨论

## 1. 讨论背景

本文件记录团队预付款、应付明细、付款记录和数据统计相关的表设计讨论结论。后续设计财务管理、数据统计、团队利润、供应商对账、银行现金账等模块时，应先阅读本文件，避免把排团成本表和财务账款表混在一起。

## 2. 老系统团队预付款页面事实

老系统页面：`/Finance/ImprestMoney.aspx`，页面名称为“团队预付款”。

页面列表主要字段包括：

- 付款单
- 类型
- 供应商
- 团号/订单号
- 发生日期
- 费用说明
- 责任计调
- 导游
- 登记人
- 预算成本
- 预付
- 已付
- 余款
- 申领详情
- 操作

老系统关键业务事实：

- 团队预付款列表每一行本质是一条团队成本/预付款项目。
- 老系统用 `CostBudgetId` 标识这条成本预算项目。
- 点击“付款”时，会基于当前 `CostBudgetId` 新增付款记录。
- `已付` 不是人工直接填在预付款列表里，而是根据付款记录汇总出来。
- `余款 = 预付 - 已付`。
- 一个预付款项目可以分多次付款。
- 一次付款也可能用于多个项目，后续通过合并付款单或分摊关系解释。
- “合并付款单”不是新的成本来源，只是把多个预付款/应付项目合并处理或打印付款单。

## 3. 新系统表职责划分

### 3.1 `dispatch_team_arrangements`

`dispatch_team_arrangements` 是团队安排成本来源表。

它回答的问题是：

- 这个成本怎么产生的？
- 属于哪个团队？
- 是酒店、大交通、车队、景区、用餐、自费、购物、地接还是附加费用？
- 供应商是谁？
- 数量、单价、预算成本、现结、挂账、预付款是多少？
- 是否需要导游报账？
- 成本如何按订单归属或多订单均摊？

它适合作为排团和成本来源，不适合作为完整财务账款主表。

### 3.2 `finance_payable_items`

`finance_payable_items` 是应付/预付明细主表，也就是财务账款项目表。

它回答的问题是：

- 财务是否需要付款？
- 应该付给谁？
- 预算成本是多少？
- 预付金额是多少？
- 已经付了多少？
- 还剩多少？
- 付款状态是什么？
- 这笔账是否已经锁账、作废或结清？

团队预付款列表如果正式接入财务链路，主表应使用 `finance_payable_items`，不是直接使用 `finance_payment_records`。

推荐字段口径：

- `source_type`：来源类型，例如 `team_arrangement`。
- `source_id`：来源单据 ID，例如 `dispatch_team_arrangements.id`。
- `team_id`、`team_no`：团队信息。
- `order_id`、`order_no`：订单归属信息，可为空。
- `resource_type`：资源类型，例如酒店、大交通、车队。
- `supplier_id`、`supplier_name`：供应商快照。
- `business_date`：发生日期。
- `cost_description`：费用说明。
- `operator_employee_id`、`operator_employee_name`：责任计调。
- `guide_id`、`guide_name`：导游。
- `created_by`、`created_by_name`：登记人。
- `budget_amount`：预算成本。
- `prepay_amount`：预付金额。
- `paid_amount`：已付金额缓存。
- `balance_amount`：余款缓存。
- `payment_status`：未付、部分付款、已付、超付等。
- `finance_locked`：是否财务锁账。

其中 `paid_amount` 和 `balance_amount` 不能人工录入，只能由后端根据付款流水和分摊明细自动计算或回写。

计算规则：

```text
paid_amount = sum(finance_payment_allocations.amount)
balance_amount = prepay_amount - paid_amount
```

### 3.3 `finance_payment_records`

`finance_payment_records` 是付款流水主表。

它记录公司实际付出去的一笔钱，例如：

- 付款日期
- 付款对象
- 付款账户
- 付款方式
- 付款金额
- 经办人
- 付款凭证
- 备注
- 是否作废

它回答的问题是：

- 钱是什么时候付出去的？
- 付给谁？
- 从哪个账户付的？
- 付了多少钱？
- 谁登记的？
- 有没有付款凭证？

付款流水不适合作为团队预付款列表主表，因为团队预付款列表中存在尚未付款的项目，而付款流水只有实际付款后才产生。

### 3.4 `finance_payment_allocations`

`finance_payment_allocations` 是付款分摊表。

它记录一笔付款冲减了哪些应付/预付项目，以及每个项目冲减了多少金额。

典型场景：

- 一个预付款项目分三次付款。
- 一笔付款合并支付多个团队或多个供应商项目。

示例：

```text
finance_payment_records
付款单 P001，付款金额 3000

finance_payment_allocations
P001 -> A 团酒店应付 1000
P001 -> B 团酒店应付 1500
P001 -> C 团酒店应付 500
```

## 4. 团队预付款页面主表结论

团队预付款页面正式接入财务后，主表应为：

```text
finance_payable_items
```

原因：

- 页面每一行是“一条需要预付或应付的账款项目”。
- 付款前也需要显示，所以不能以付款流水为主表。
- 预算成本、预付、已付、余款、付款状态都属于账款项目维度。
- 点击“付款”时，应带 `finance_payable_items.id` 新增付款记录和付款分摊。
- “合并付款单”应勾选多个 `finance_payable_items.id`。

页面字段与表字段建议对应：

| 页面字段 | 推荐来源 |
| --- | --- |
| 类型 | `finance_payable_items.resource_type` |
| 供应商 | `finance_payable_items.supplier_id`、`supplier_name` |
| 团号/订单号 | `finance_payable_items.team_no`、`order_no` |
| 发生日期 | `finance_payable_items.business_date` |
| 费用说明 | `finance_payable_items.cost_description` |
| 责任计调 | `finance_payable_items.operator_employee_name` |
| 导游 | `finance_payable_items.guide_name` |
| 登记人 | `finance_payable_items.created_by_name` |
| 预算成本 | `finance_payable_items.budget_amount` |
| 预付 | `finance_payable_items.prepay_amount` |
| 已付 | `finance_payable_items.paid_amount` |
| 余款 | `finance_payable_items.balance_amount` |
| 付款 | 新增 `finance_payment_records` 和 `finance_payment_allocations` |
| 合并付款单 | 多选 `finance_payable_items.id` |

## 5. 为什么不直接合并到 `dispatch_team_arrangements`

`dispatch_team_arrangements` 和 `finance_payable_items` 会有部分字段重复，例如团队、供应商、资源类型、预算成本、预付款金额。这是业务快照，不是无意义重复。

不建议完全合并的原因：

- 排团安排经常修改，财务付款记录需要稳定账款对象。
- 财务需要锁账、作废、调整、结清等状态，不能和排团编辑状态混用。
- 应付来源后续不一定只有团队安排，也可能来自导游结算、地接补差、供应商调整、冲抵等。
- 财务统计希望统一查应付账款表，而不是分别查多个业务来源表。
- 已经付款后，如果排团成本被修改，不能直接覆盖历史财务账。

因此更合理的职责是：

```text
dispatch_team_arrangements
= 排团成本来源

finance_payable_items
= 财务确认后的应付/预付账款快照
```

## 6. `finance_payable_items` 的生成时机

不建议在计调每次保存团队安排时立即无脑生成 `finance_payable_items`。

原因是团队安排阶段经常会改供应商、数量、价格、现结、挂账、预付、导游报账状态，过早生成财务账会导致频繁同步、作废或重建。

推荐生成时机：

```text
计调审核通过，或团队安排提交财务审核时生成 finance_payable_items
```

更推荐使用“计调审核通过后生成”，因为这代表业务成本已经确认，财务可以提前看到待付款项。

生成后修改规则：

- 未付款：允许按来源成本同步更新 `finance_payable_items`。
- 已部分付款或已付：不能直接覆盖，应生成调整记录、作废重开或走财务调整流程。
- 已财务锁账：原则上禁止业务侧直接修改金额、供应商、付款对象等关键字段。

## 7. 表关系图

```text
dispatch_team_arrangements
团队安排成本来源
        │
        │ 计调审核通过或提交财务后生成
        ▼
finance_payable_items
应付/预付明细主表
保存预算成本、预付、已付、余款、付款状态
        │
        │ 点击付款，产生付款分摊
        ▼
finance_payment_allocations
付款分摊表
记录某次付款冲减了哪条应付/预付项目
        │
        │ 属于某一次真实付款
        ▼
finance_payment_records
付款流水主表
记录真实付款日期、账户、对象、金额、凭证、经办人
```

一个项目分多次付款：

```text
finance_payable_items
酒店预付款 400
        │
        ├── allocation 100 -> payment_record 第一次付款
        ├── allocation 200 -> payment_record 第二次付款
        └── allocation 100 -> payment_record 第三次付款
```

一笔付款支付多个项目：

```text
finance_payment_records
一次付款 3000
        │
        ├── allocation 1000 -> A 团酒店应付
        ├── allocation 1500 -> B 团酒店应付
        └── allocation 500  -> C 团酒店应付
```

## 8. 对数据统计的影响

后续财务管理和数据统计不能直接从前端页面数组或临时 JS 计算金额。

应付、预付、已付、余款、付款统计、供应商对账、团队利润等应以后端财务表为准：

- 应付/预付项目：`finance_payable_items`
- 付款流水：`finance_payment_records`
- 付款分摊：`finance_payment_allocations`
- 团队安排成本来源：`dispatch_team_arrangements`
- 订单成本归属：`dispatch_team_arrangement_order_allocations`

统计查询建议按以下维度预留索引和汇总能力：

- 租户
- 团队
- 供应商
- 资源类型
- 责任计调
- 导游
- 业务日期
- 付款日期
- 付款状态
- 财务审核状态
- 是否删除

数据量增大后，财务统计、经营统计、付款汇总、供应商对账不应长期直接实时扫明细表，应考虑汇总表、缓存、物化视图或定时任务。

## 9. 当前阶段建议

如果只做团队安排页面内的临时预付款展示，可以暂时读取 `dispatch_team_arrangements.prepaid_amount`。

如果开发正式“团队预付款”财务页面，应按以下方式推进：

1. 先设计 `finance_payable_items`、`finance_payment_records`、`finance_payment_allocations`。
2. 由计调审核通过或提交财务动作生成 `finance_payable_items`。
3. 团队预付款列表以 `finance_payable_items` 为主表。
4. 点击付款时新增付款流水和付款分摊。
5. 后端自动维护 `paid_amount`、`balance_amount`、`payment_status`。
6. 已付款或财务锁账后，不允许排团修改直接覆盖财务账，必须走调整或作废流程。

最终结论：

```text
dispatch_team_arrangements 是成本来源。
finance_payable_items 是团队预付款和应付账款的主表。
finance_payment_records 是真实付款流水。
finance_payment_allocations 是付款与应付项目之间的分摊关系。
```
