# 老系统调研：销售管理 / 团队管理

调研日期：2026-06-22

## 1. 团队管理入口

老系统 `销售管理 / 团队管理` 入口为：

- `/sale/GroupManage.aspx`

同一个页面按 `LineType` 参数切换团队类型：

- `LineType=2`：散拼
- `LineType=3`：整团
- `LineType=4`：散团
- `LineType=5`：单项

首页“我的收客团队”里的 `散拼 / 散团 / 整团 / 单项` 也都跳到同一个团队管理页，只是参数不同。

结论：新系统不应给不同团队类型拆不同主表。应使用统一团队主表，通过 `team_type` 字段区分团队类型。

## 2. 团队列表字段

老系统团队列表表头：

- 类型
- 团号
- 客户
- 团队名称
- 天数
- 开始
- 结束
- 出发地
- 预控 / 实收
- 导游信息
- 导
- 交
- 住
- 车
- 景
- 餐
- 其
- 自
- 购
- 地
- 进度

列表中的 `导 / 交 / 住 / 车 / 景 / 餐 / 其 / 自 / 购 / 地` 是后续计调安排入口，分别进入导游、大交通、住宿、用车、景区、用餐、其他、自费、购物、地接等团队安排页面。

结论：团队主表至少要能支撑列表展示：团队类型、团号、客户摘要、团队名称、天数、出团/结束日期、出发地、预控人数、实收人数、导游摘要、各安排状态。

## 3. 查询条件

老系统查询条件：

- 团号 / 团队名称 / 备注
- 客户单位 / 业务员
- 导游
- 操作计调
- 出发地
- 部门
- 业务类型
- 订单状态：未处理、已确认、已取消、无订单
- 出团日期始 / 止
- 添加日期
- 天数
- 团队状态：全部团队、未发团、已发团、已停售、已取消

结论：新系统列表接口要按这些维度预留筛选能力，但不能为了筛选一次性加载所有下拉数据。部门、业务类型、人员下拉按需加载。

## 4. 新增团队入口

团队管理页顶部有四个新增入口：

- 散拼：`LineAdd.aspx?menu=A1&LineType=2`
- 整团：`LineAdd.aspx?menu=A1&LineType=3`
- 散团：`LineAdd.aspx?menu=A1&LineType=4`
- 单项：`SingleBusinessAdd.aspx?menu=A1`

其中 `散拼 / 整团 / 散团` 共用同一个新增/编辑页面 `LineAdd.aspx`，只靠隐藏字段 `LineType` 区分类型。

`单项` 使用独立页面 `SingleBusinessAdd.aspx`，录入字段更多，包含客户、来程返程、价格、备注和游客名单等订单化内容。但保存后仍进入同一个团队管理列表，类型显示为 `单项`。

结论：数据库仍建议统一团队主表。单项可以有补充表或订单表字段承接它特有的来返程、客户、价格和游客名单信息，不要把单项团队单独做一套主表。

## 5. 散拼 / 整团 / 散团基础字段

三类团队新增页共用字段：

- 业务类型
- 国内 / 国际
- 线路名称
- 操作备注
- 接团城市：省 / 市 / 区县
- 出团日期
- 出团类型：每天发、每周发、不定期
- 周一至周日勾选
- 接待标准
- 产品主题
- 旅游天数
- 截止收客
- 单人房差
- 预控人数
- 隐藏字段 `LineType`

结论：产品模板和团队主表字段高度重叠，但含义不同：

- 产品模板是可复用线路资料。
- 团队是某个出团日期下的执行对象。

新系统不能只保存产品模板就当团队。创建团期或创建团队时，应落到统一团队主表。

## 6. 单项业务字段差异

单项新增页主要字段：

- 团队信息：业务类型、国内/国际、发团日期、旅游天数、预控人数、产品信息、团队名称、操作备注
- 行程说明：来程信息、返程信息、接送站、航班号/车次、航班时间、抵达时间
- 接送相关：接机标识、接送备注
- 客户信息：客户单位、联系人、联系电话、客户团号、业务员、收客计调
- 价格信息：成人、儿童、儿童不占床、老人、全陪、单房差、机票、火车票、车费、导服、餐费、房费、门票、自费、杂费、附加费等
- 附加说明：费用说明、确认说明、订单备注
- 游客名单：姓名、证件号、性别、出生年月、客户类型、年龄、联系电话、单人备注

结论：单项业务更像“团队 + 初始订单 + 游客名单”的合并录入页。新系统可以拆成更清楚的表和接口，但页面入口要让用户一口气录完关键资料。

## 7. 团队操作页

点击团号进入：

- `/sale/TeamOperation.aspx?GroupId=团队ID`

该页主要展示团队下订单，表头包括：

- 选择
- 订单信息
- 接送备注
- 客源地
- 客人
- 人数
- 价格详情
- 应收
- 已收
- 余额
- 费用说明
- 订单备注
- 日期 / 预定人
- 状态

结论：团队是订单的归属对象。订单、游客、收款、费用变更都应挂到团队 ID 下。

## 8. 建表方向

建议后续新系统按以下方向设计：

- `sales_teams`：统一团队主表，保存散拼、整团、散团、单项。
- `sales_team_prices`：团队价格表，保存团队按客户分类或价格项的成人、儿童、老人、单房差、附加费等价格。
- `sales_orders`：订单主表，保存客户订单、订单状态、人数、应收、已收、余额等。
- `sales_order_guests`：游客名单表。
- 单项业务的来返程、接送和初始价格，可以先落订单相关表或单项补充表，避免污染团队主表。

本轮如果只开发“产品团期管理”，应只把它作为创建 `sales_teams.team_type = sanpin` 的入口，不新增单独的 `团期主表`。

## 9. 待甲方确认

- 新系统里 `散团` 与 `整团` 在业务规则上的差异是否仅为类型标签，还是后续报价、订单、统计口径也不同。
- `单项` 是否需要保留老系统“一页录团队、订单、游客”的录入体验。
- 团号生成规则中 `CS-SP-BK`、`CS-DW-CS` 等前缀具体含义是否需要完全沿用。
- 团队状态 `未发团 / 已发团 / 已停售 / 已取消` 的触发规则是否由日期自动判断，还是允许人工切换。
- `预控 / 实收` 中实收括号三段数字的准确口径需要确认，目前观察像成人/儿童/其他分类人数。
